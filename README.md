# LLM-based Scraping for the Extraction and Linking of German-language Fact Checks

This repository contains the code and data pipeline for the bachelor's thesis in the Computer Science program at Heinrich Heine University Düsseldorf (PO 2016). The goal of the project is to automatically crawl German-language fact-check articles, structurally extract them using Large Language Models (LLMs), and convert them into a semantically linked knowledge graph (Open Claims model).

---

## 📂 Folder Structure & Data Storage

The project is strictly separated by responsibilities. The generated and required data is managed in the following directories:

*   **`data/input/`**: Contains input files, primarily `url_list.json`. 
*   **`data/raw/`**: The generated SQLite databases are stored here. This includes the cache for the raw HTML pages (`html_cache`) and the structured fact-check storage (`factcheck_manager`). When loading existing databases, the pipeline always references this directory.
*   **`data/output/`**: The target directory for final exports of the main pipeline (`factchecks_export.csv` and the RDF knowledge graph `faktchecks_export.ttl`).
*   **`evaluation/evaluation_data/output/`**: The target directory for all metrics and results generated by the evaluation scripts.
*   **`logs/`**: Contains the automatically generated log files (`app.log` for general info and `debug.log` for in-depth error analysis).

## ⚙️ Configuration Before Start

Before the scripts can be executed, the following files should be checked and populated if necessary:
Before the scripts can be executed, the following files should be checked and populated if necessary:

1.  **`.env` File (API Key)**: You must create a `.env` file in the project's root directory. This file is required to securely store your KI Connect API key. Add the following line to it:
    ```env
    KICONNECT_API_KEY=your_api_key_here
    ```
2.  **`config/portals.json`**: The core for code generation and the crawler. The target portals are defined here (e.g., with the portal's name and a `factcheck_example` link).
3.  **`config/filter_rules.json`**: Controls the rule-based URL filter during crawling. Using `include` (at least one term must appear in the URL) and `exclude` (must not appear in the URL), it strictly decides whether a discovered URL is added to the cache.
4.  **`data/input/url_list.json`**: Must be filled with specific target URLs if you intend to run the pipeline using the `--use-url-list` flag.
5.  **`config/few_shots.json`** *(Experimental)*: A theoretical approach to provide the LLM with specific examples (few-shot prompting) for extraction. *Note: This feature is implemented but not yet fully tested.*

## 🚀 Entry Points & Execution

The project is controlled via three central main scripts, which are executed via the command line interface (CLI).

### 1. `main_generator.py` (Code Generation)
This script compares the portals stored in `config/portals.json` with the already existing parsers and preprocessors. If parser or preprocessor scripts are missing for a portal, the LLM-based generators are automatically started to generate the code based on the `factcheck_example`.

### 2. `main_runtime.py` (The Main Pipeline)
The execution script for productive operation. It controls the entire workflow from URL input to the final knowledge graph. 
**Important:** The `main_runtime.py` itself does **not** generate any code. Missing parsers or preprocessors must strictly be created beforehand via `main_generator.py`.

*Tip: For testing purposes, using a predefined URL list (`--use-url-list`) is highly recommended, as full manual crawling of sitemaps is extremely time-consuming.*

**Available CLI Arguments:**
*   `--html-db-version <name>`: Specifies the version name for the HTML cache database. The behavior depends on the selected mode: If creating or copying, this name is used to generate the filename for the *new* database. If loading, it identifies the *existing* database file to be opened from `data/raw/`.
*   `--html-db-version-mode <mode> [source_path]`: Expects 1 or 2 arguments. The first argument defines the mode (`load` for existing, `copy` for duplicates). If no mode is provided, it defaults to creating a new database. The second argument is the full source path (only required if mode is `copy`).
*   `--factcheck_db_version <name>`: Specifies the version name for the fact-check database. Just like the HTML cache, this name dictates the filename of the *newly created* database (in `create`/`copy` mode) or specifies exactly which *existing* database to open (in `load` mode) within `data/raw/`.
*   `--factcheck-db-version-mode <mode> [source_path]`: Same logic as the HTML mode, applied to the FactCheck manager.
*   `--use-url-list`: Skips the sitemap crawler and uses the links defined in `data/input/url_list.json` instead.
*   `--use-preprocessor`: Activates the preprocessing (shortening/cleaning) of the HTML before extraction.
*   `--use-generated-parser`: Uses the locally generated parser scripts instead of direct extraction by the LLM.
### 3. `main_evaluation.py` (Evaluation & Testing)
Controls the systematic evaluation of the pipeline's quality. All outputs are saved to `evaluation/evaluation_data/output/`.

**Available CLI Arguments:**
*   `--run-llm-directly-ground-truth`: Tests the direct LLM extraction against the ground truth.
*   `--run-llm-preprocessed-ground-truth`: Tests the LLM extraction (including preprocessor) against the ground truth.
*   `--run-parser-ground-truth`: Tests the generated parsers against the ground truth.
*   `--run-claims-kg-ground-truth`: Compares the ClaimsKG data with the ground truth.
*   `--run-crawl-evaluation`: Executes the crawl evaluation (*Warning: May take a very long time*).
*   `--run-all-extraction`: Runs all the extraction evaluations mentioned above sequentially (without crawl evaluation).
*   `--run-all`: Runs all available evaluations.
*   `--language <language>`: Sets the language for the ground truth tests (Default: `english`, Option: `german`).
